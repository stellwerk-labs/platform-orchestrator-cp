# Control Plane v3.2.0

## Module Drafts and Resource Type interfaces

Module Drafts separate authoring from publication. Save and inspect revisions
under one intended SemVer, capture a saved revision for a specific Project and
Environment, then explicitly deploy that immutable snapshot through the normal
Runner. Saving does not capture, deploy, or reserve a version. Later edits leave
earlier captures, queued work, and retained deployments unchanged.

Publishing closes the Draft and creates a separate immutable Proposed Version
from the exact stored revision. Promotion to Default is a separate explicit
action. Existing Proposed, Default, and historical Versions remain unchanged,
and Pins remain authoritative. A Module without a Default can be tested through
a Rule scoped to both Project and Environment.

Resource Types gain immutable interface versions. Historical global and
organization-specific contracts become version 1 with their original content and
timestamps. Existing Module Versions retain their exact interface binding when a
later interface is published. Older HTTP callers that omit the interface version
continue to select version 1.

## Compatibility

The Control Plane shared Go SDK uses the separate
`github.com/stellwerk-labs/platform-orchestrator-cp/shared/v3` module path. This
Go major version can require source changes to imports and generated-client
interface implementations; it does not remove existing HTTP operations. New
authoring and test routes require matching Control Plane, Data Plane, and
gateway support. When a requested route is unavailable, clients must report an
error rather than substitute a published Default.

## Upgrade and recovery

Control Plane migrations 49, 50, and 51 retain interface versions, Draft
revisions, and test snapshots. Upgrade the compatible Data Plane before enabling
the new Control Plane workflows, then update the Console and clients. Older
Control Plane or Data Plane binaries refuse the new schemas. Do not use an
old-binary Helm downgrade or destructive Down migrations as recovery. Keep the
compatible schema and use a schema-compatible image or forward fix. A database
restore is a separate recovery operation; back up databases, configuration, and
outstanding work first.

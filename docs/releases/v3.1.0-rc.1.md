# Control Plane v3.1.0-rc.1

This is a prerelease for testing the coordinated plugin-capable release set. Use
this candidate for evaluation before the stable release.

This release adds the plugin host for operator-installed, first-party Stellwerk
plugins at contract level `v1alpha`. The host is off by default. `v1alpha` is
not a stable partner contract; it may change in a later minor release.

## What changes

- Plugin host switch `PLUGIN_HOST_ENABLED` (default `false`). Toggle it for all
  Control Plane replicas together.
- Plugin discovery `GET /orgs/{orgId}/plugins` reports `contract_level: v1alpha`
  and one availability state per plugin: `available`, `not_installed`,
  `not_enabled`, `not_entitled`, `incompatible` or `unavailable`. Clients invoke
  registered operations by operation ID through the Orchestrator; delegated
  plugin calls are bound to audience, operation, request body, expiry and
  idempotency key.
- Plugin Manager: a database-backed, audited platform operator API
  (`/plugin-packages`, `/plugin-installations`, `/plugin-entitlement-bundles`,
  `/plugin-audit-events`). Mutation commands take a reason, an expected revision
  and an idempotency key. Changes apply without a Control Plane restart.
  Activation binds an installation to the installation UUID, verified package
  digest and migration generation that the running plugin reports. Upgrades
  switch registrations atomically. Uninstall waits for unsettled plugin work
  (`plugin_work_unsettled`), reinstall keeps the installation UUID, purge is
  final.
- Plugin Manager operators are authorised by IAM (`plugin_manager_read`,
  `plugin_manager_write`). Recording an installation identity requires a
  matching IAM workload binding, otherwise
  `409 plugin_workload_binding_missing`. The installation's identity must be an
  IAM platform principal (a service user that belongs to no organisation and
  holds no role), otherwise `409 plugin_service_user_not_platform_principal`,
  and the admission checker must be a platform principal with a static token,
  otherwise `409 plugin_admission_checker_not_platform_principal`. Enablement
  changes do not repeat the workload-identity validation, but operator
  authorization still requires IAM.
- One installation serves several organisations: one runtime, one platform
  principal and one plugin database for every organisation it is enabled for.
  Each organisation has its own enablement, timezone and approval policies, and
  Orchestrator confines every effect to one organisation. The earlier rule that
  an installation serves only the organisation of its service user, with
  `plugin_service_user_organization_mismatch` and `plugin_enablement_limit`, is
  gone.
- `PUT /plugin-installations/{id}/organization-mode` sets `selected` (the
  default) or `all`, with `default_timezone` and `default_approval_policies` for
  the enablements Orchestrator creates. `all` enables every active organisation
  in one audited command and every organisation created later inside its
  creation transaction (the enablement is removed again if the creation fails).
  An organisation opts out by disabling its enablement; Orchestrator never
  re-enables it, across mode switches and restarts. Removing an enablement while
  the mode is `all` is refused with `409 plugin_serves_all_organizations`.
  Uninstall removes every enablement and returns the mode to `selected`. Reads
  show `organization_mode`, `organization_defaults` and `pending_organizations`
  (organisations Orchestrator could not enable because the plugin host was off
  or the organisation limit was reached; setting `all` again enables them).
- Orchestrator registers the capabilities of the package manifest in IAM for
  every enabled organisation, as its own internal identity, right after
  enabling, after every activation and every minute for drift. The plugin
  registers nothing. Each enablement shows `capability_registration`
  (`registered`, `pending` or `failed` with a detail). Disabling keeps the
  registration.
- Package manifests are checked for collisions: capabilities are objects with
  `id`, `display_name`, `description`, `category`, `level` and `scopes` (a plain
  string capability is refused with `plugin_manifest_invalid`), the `id` must be
  `plugin.<plugin id>.<name>` and unique, UI route prefixes use the Console's
  lowercase spelling, and an exact route prefix held by another installation is
  refused at activation (`409 plugin_registration_conflict`).
- Signed offline entitlements (COSE) bound to one installation and either one
  organisation or, with the organisation claim absent, the whole installation
  (an installation-wide grant, which also covers organisations created later),
  imported through the API. An installation-wide grant can carry
  `limits.organizations`; Orchestrator checks it when it enables an organisation
  and refuses with `409 plugin_organization_limit` (an organisation created at
  the limit is still created and listed as pending). All enabled organisations
  count, including those with their own grant. A lower limit on renewal blocks
  only new enablements; it never disables an existing organisation. A valid
  organisation grant, including grace, takes precedence without combining
  feature sets. When it expires after grace or is revoked, a valid or grace
  installation-wide grant takes over. A future or unverifiable organisation
  grant does not trigger this fallback. Renewal restores organisation-grant
  precedence, and all grant and audit evidence is retained. Status reads carry
  `grant_scope`, and installation reads show the grants. Production mode rejects
  development trust. During a grace period forward work continues with the
  warning `plugin_entitlement_grace`. Licence or trust material never stops the
  Control Plane; only the affected plugin degrades.
- Scoped plugin grants for Module Version, Pin and Deployment operations with
  fences, receipts and recovery. Protected Deployment material stays on the
  user's Orchestrator path.
- Resource event journal over HTTP for organisations with a subscribing
  installed plugin, 30 days retention by default
  (`PLUGIN_EVENT_JOURNAL_RETENTION`), gap markers after a paused subscription;
  expired cursors return `plugin_resource_cursor_expired`.
- `POST /orgs/{orgId}/projects/{projectId}/envs/{envId}/deployments/{deploymentId}/actions/acknowledge-outcome`
  records an audited acknowledgement of an unknown outcome of a
  plugin-dispatched Deployment (permission `deployment.outcome.acknowledge`,
  reason required).
- `DEPLOYMENT_ADMISSION_IDENTITY` names the one identity that the Data Plane's
  Deployment admission callbacks must come from, for every organisation, so an
  organisation created later deploys without a configuration change or a
  restart. Orchestrator asks IAM on every callback that it is a static-token
  platform principal. Any other identity, such as a service user of an
  organisation, is refused with `403 deployment_admission_service_forbidden`,
  and `503 authorization_unavailable` while IAM cannot answer. Unset,
  Orchestrator refuses every callback; a value that is not the canonical UUID of
  a service identity stops the start-up.
- Deployment admission conflicts carry stable codes: `environment_busy`,
  `pin_protection`, `module_version_lifecycle`, otherwise
  `deployment_admission_conflict`.

## Behaviour without plugins

With the host off, the Plugin Manager API answers `404 plugin_host_disabled` and
the event journal writes nothing. Module Management and Pins remain available.
Ordinary Deployments still require the Deployment admission identity configured
below. The admission codes above are new body codes on existing 409 responses;
statuses and messages are unchanged.

## Data, migration and recovery

Back up the Control Plane database before upgrading. Migrations 33 to 48 are
additive (plugin operations, grants, admission guards, event journal,
entitlements, Plugin Manager, several organisations per installation with
capability registrations, the organisation mode and installation-wide grants).
Numbers 27 to 32 are intentionally unused. Migration 25 narrows an existing
constraint guard to its active table; every database that completed 25 already
holds that constraint, so no state diverges.

The Control Plane applies migrations 33 to 48 when it starts; they add tables
and initialize plugin state. For recovery, switch the plugin host off or use a
compatible post-upgrade Helm revision with the new binaries and schema. A
configuration rollback (`helm rollback <release> <revision>`) keeps the data; it
is not a database downgrade or proof of compatibility with older binaries. Do
not go back to chart 0.7.0 or Control Plane 3.0.0: Control Plane 3.0.0 starts on
the newer schema without checking it, and IAM 2.4.0 refuses it, which stops the
API. From 3.1.0 the Control Plane refuses to start on a schema newer than its
own migrations ("database schema version N is newer than this binary's latest
migration 48"). Down migrations are not a rollback procedure; the Down steps of
migrations 35 to 41, 44, 45, 47 and 48 refuse while plugin state of their kind
exists (unsettled dispatches, admission guards, extension events, entitlement
grants, Plugin Manager audit, purged installations, an installation enabled for
several organisations or serving all of them, installation-wide grants).

## Known limitations of `v1alpha`

Stellwerk is the only supported publisher. All organisations of an installation
share one plugin database, so a plugin bug can mix their data inside it, and a
compromised plugin reaches every enabled organisation within the plugin boundary
(Orchestrator still refuses every effect across organisations). Events use the
HTTP journal; generic NATS subscription provisioning is not part of `v1alpha`.
Keyless Sigstore publishers, synchronous policy hooks, same-origin UI and
migration from earlier in-process plugins are not supported. Plugin workloads
need Kubernetes 1.30 or newer (see the plugin runtime release).

## Go contract

`shared/v2.1.0` publishes additive packages under
`github.com/stellwerk-labs/platform-orchestrator-cp/shared/v2`: `plugincontext`,
`pluginstatus` and the generated plugin, admission and Plugin Manager client. It
requires Go 1.26.2. The application tag does not publish the SDK.

## Upgrade actions

This is the first release with the Plugin Manager. A fresh install must
configure the required identities before enabling plugin or admission features.
If you ran a pre-release build with a plugin installed, reinstall the plugin; an
upgrade in place is not supported:

- The manifest of a registered package must declare capabilities as objects.
  Packages stored by earlier builds, with string capabilities, no longer decode.
  Register the package again from the plugin's new release.
- The installation's identity must be a platform principal, and the admission
  checker a static-token platform principal. A service user of an organisation
  is refused. Create both again with `octl plugin-manager create-identities`
  (needs CLI 2.1.0 and IAM 2.5.0).
- The Data Plane's Deployment admission identity must be a static-token platform
  principal as well. Create one with `POST /platform-principals` (or reuse the
  admission checker), store its token in the Data Plane's
  `DEPLOYMENT_ADMISSION_CORE_BEARER_TOKEN_FILE`, and set its UUID in
  `DEPLOYMENT_ADMISSION_IDENTITY` (chart profile `deploymentAdmission`).
  Orchestrator no longer reads the pre-release
  `DEPLOYMENT_ADMISSION_IDENTITIES_FILE`; until you set the new variable,
  admissions fail with `403 deployment_admission_service_forbidden`.
